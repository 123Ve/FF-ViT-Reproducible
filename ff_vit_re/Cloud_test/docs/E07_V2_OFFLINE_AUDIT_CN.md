## 已确认的源码问题与修订

1. **Full 大块申请可能不前进。** 旧 `pump_bulk` 每次申请全部 sndbuf；lwIP 的
   sndbuf 是字节信用，不保证一次原子写所需的 pbuf/segment 分配成功。
   测试将单次可分配上限降至 1024，而发送信用保持更大，旧代码只留下前缀，
   断言负载不完整；V2 最大块 1460，ERR_MEM 时减半，再由 ACK 和主循环继续发送。
   这是模拟的 lwIP 边界条件，不是实际板端堆碎片或 pbuf 泄漏的证明。
2. **旧客户端超时漏计部分负载。** BufferedReader.read(完整负载) 在内部已接收
   一部分后超时，外层计数不能反映这部分数据。V2 每次 recv 即计数，超时日志保留进度。
   旧记录额外 319 字节符合响应前缀，但不能据此断言当时一个负载字节也未到达。
3. **超时是读取空闲超时，不是事务截止时间。** 持续少量来数据可以使旧请求
   长时间不结束。V2 在每次发送与读取前检查同一绝对 deadline，实测 socket 滴流测试会结束。
4. **失败阶段仍计算收益。** V2 保留失败统计和成功帧的初步字节比，
   但将失败配对的带宽节省与能耗差设为 null，并给出原因。

新增 UART `BULK_STALL` 输出发送 offset、总长度、sndbuf、队列长度、远端窗口和内存重试次数。
客户端 `transaction_failure` 输出命令、请求 ID、已收总字节、预计长度和部分负载长度。
保留失败并终止当前捕获，不自动重跑拼接或把失败标为 COMPLETE。
UART 的 bulk 进展是应用层入队进展，不是已 ACK 或 PHY 发出进展。
所有字节入队后，最后一块的暂时输出失败可由当前 lwIP 的输入/重传定时器继续处理；
小型 JSON/prefix 路径仍会在写入失败时中止连接，不能声称所有发送路径都采用相同的内存重试。

## 接收慢的已知限制与尚未确定的贡献

输入是 602112 字节的 int32 固定 tensor，不是压缩 JPEG。
旧 BSP 的 TCP_WND=2048 仅约 1.4 MSS；PS 应用 -O0；逐字节解析还逐字节访问参考输入。
这些限制均由源码和构建配置确认，V2 分别提供 32768 窗口、分块校验和 -O2。
但 92.9 ms 的各项贡献尚不能从现有日志拆分；不把所有时间归因于窗口、CPU 或链路。
Host send 完成表示 OS 已接收发送数据，不表示板卡已收到整帧。
一个连接上的串行事务也没有输入传输与推理跨帧重叠；不能用 PL 核吞吐替代系统吞吐。
